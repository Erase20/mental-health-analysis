# Docker、异步任务、并发与监控升级计划

## 一、目标架构

升级后的服务关系：

```text
浏览器
  → Nginx / Vue 静态文件
  → Flask / Gunicorn API
  → Redis Broker
  → Celery 分析 Worker
  → Celery 报告 Worker
  → Celery 导入 Worker
  → MySQL
  → MinIO / S3 报告存储
  → Prometheus + Grafana + Flower + Sentry
```

目标：

1. 使用 Docker Compose 一键启动全部服务。
2. 长时间分析改成异步任务。
3. 前端能够查看任务状态和进度。
4. 控制用户并发、Worker 并发和数据库压力。
5. 能监控 API、Celery、Redis、MySQL 和任务失败。

## 二、实施顺序

不要同时开始所有工作。建议按下面顺序：

```text
数据库迁移
→ Docker 容器化
→ Celery 异步任务
→ 并发和可靠性
→ 监控告警
→ 压测与 CI/CD
```

原因：

- 没有数据库迁移，新增任务表会很难管理。
- 没有 Docker，Redis、Celery、MySQL 的启动和联调成本很高。
- 没有异步任务，监控对象和并发控制都缺少业务基础。

### 后端 Dockerfile 示例

```dockerfile
FROM python:3.10-slim

ENV PYTHONDONTWRITEBYTECODE=1
ENV PYTHONUNBUFFERED=1

WORKDIR /app

RUN apt-get update \
    && apt-get install -y --no-install-recommends fonts-noto-cjk \
    && rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

CMD ["gunicorn", "-b", "0.0.0.0:5000", "-w", "2", "run:app"]
```

### 前端 Dockerfile 示例

```dockerfile
FROM node:20-alpine AS build

WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
```

### Compose 服务示例

```yaml
services:
  api:
    build: ./backend
    env_file: .env
    depends_on:
      mysql:
        condition: service_healthy
      redis:
        condition: service_healthy
    ports:
      - "5000:5000"

  redis:
    image: redis:7-alpine
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s

  worker-analysis:
    build: ./backend
    command: celery -A app.celery worker -Q analysis_queue -c 2
    env_file: .env
    depends_on:
      - redis
      - mysql
```

### 验收标准

- `docker compose up --build` 能从空环境启动。
- `docker compose down` 后数据库数据不会丢失。
- 容器重新启动后账号、数据、报告记录仍然存在。
- PDF 中文字体在 Linux 容器中可以正常显示。

### 常见问题

- Windows 字体路径在 Linux 容器中不存在。
- 前端开发代理不能用于容器生产环境。
- 本地上传目录和报告目录会在容器重建后丢失。
- MySQL 启动比 Flask 慢，需要健康检查。

## 五、阶段三：Celery 异步任务

### 目标

```text
POST /api/analysis/run
→ 立即返回 202 和 task_id
→ Worker 执行分析
→ 前端查询任务状态
```

### 任务清单

- [ ] 将 Celery 初始化改为应用工厂兼容方式。
- [ ] 创建 `app/tasks/analysis_tasks.py`。
- [ ] 创建 `app/tasks/report_tasks.py`。
- [ ] 创建 `app/tasks/import_tasks.py`。
- [ ] 新增任务状态查询接口。
- [ ] 新增任务取消接口。
- [ ] 前端增加任务提交、进度轮询和结果跳转。
- [ ] 任务失败时写入明确错误原因。
- [ ] 报告文件从本地目录迁移到 MinIO 或 S3。

### 任务拆分

```text
analysis_queue：特征工程、KMeans、RandomForest
report_queue：PDF 生成
import_queue：CSV/Excel 清洗和批量入库
```

### 不要这样写

```python
task = run_analysis.delay(...)
result = task.get()
```

这样会阻塞 Flask 请求，相当于又变回同步。

### 正确的分析接口

```python
task = run_analysis_task.delay(
    dataset_id=dataset_id,
    user_id=g.current_user.id
)

return jsonify({
    'code': 202,
    'message': '任务已提交',
    'data': {'task_id': task.id}
}), 202
```

### 任务进度示例

```python
@celery.task(bind=True)
def run_analysis_task(self, dataset_id, user_id):
    self.update_state(
        state='PROGRESS',
        meta={'percent': 20, 'message': '正在清洗数据'}
    )
```

### 幂等设计

为任务生成幂等键：

```text
user_id
dataset_version_id
analysis_type
参数哈希
代码版本
```

如果相同任务已经在执行，直接返回已有 `task_id`，不要重复训练。

### 重试策略

```python
@celery.task(
    bind=True,
    autoretry_for=(ConnectionError, TimeoutError),
    retry_backoff=True,
    max_retries=3
)
```

数据错误、模型输入错误等永久失败不应无限重试。

### 验收标准

- 分析接口 1 秒内返回 `task_id`。
- 刷新页面后任务进度仍然存在。
- Worker 重启后未完成任务可以继续或明确标记失败。
- 同一幂等键不会生成重复报告。

## 六、阶段四：并发与可靠性

### 线程和 Worker 分工

Flask/Gunicorn：

```text
处理短 HTTP 请求
不执行长时间机器学习训练
```

Celery Worker：

```text
处理分析、PDF 和导入任务
按任务类型拆分队列
```

### 建议并发

模型训练是 CPU 密集任务：

```bash
celery -A app.celery worker -Q analysis_queue -c 2
```

报告生成相对轻量：

```bash
celery -A app.celery worker -Q report_queue -c 4
```

具体并发数应通过压测确定，不能简单乘以很大的数字。

### 任务清单

- [ ] 每个用户限制同时执行一个分析任务。
- [ ] 每个用户限制报告生成频率。
- [ ] 每个队列设置最大长度。
- [ ] 队列满时返回排队中，而不是无限接收。
- [ ] 使用数据库状态表记录任务。
- [ ] 增加任务超时。
- [ ] 增加指数退避重试。
- [ ] 增加任务取消。
- [ ] 报告文件使用 MinIO/S3。
- [ ] 数据库查询增加索引。
- [ ] 数据导入使用分批提交。
- [ ] 避免在请求中执行 `.all()` 加载全部数据。
- [ ] 测试 10、50、100 个并发的行为。

### 并发状态图

```text
用户提交任务
→ PENDING
→ STARTED
→ PROGRESS
→ SUCCESS

异常分支：
STARTED
→ RETRYING
→ SUCCESS 或 FAILURE
```

### 验收标准

- 20 个并发分析请求不会压垮 API。
- 用户收到明确排队提示。
- 不会因重复点击生成重复任务。
- 数据库连接数保持稳定。
- Worker 失败后任务状态准确。

## 七、阶段五：监控与日志

### 最小监控组合

第一轮：

```text
Flower
Sentry
结构化日志
/health/live
/health/ready
```

第二轮：

```text
Prometheus
Grafana
Redis Exporter
MySQL Exporter
```

### 必须监控的指标

API：

```text
请求数量
请求耗时
4xx / 5xx
数据库连接池
```

Celery：

```text
排队任务数
执行中任务数
成功数
失败数
重试数
任务耗时
```

Redis：

```text
内存
连接数
队列长度
```

MySQL：

```text
连接数
慢查询
锁等待
InnoDB 事务
```

业务：

```text
分析任务成功率
报告生成耗时
导入数据条数
每个用户并发任务数
```

### 日志要求

使用结构化 JSON 日志：

```json
{
  "timestamp": "2026-09-18T12:00:00Z",
  "level": "INFO",
  "request_id": "abc123",
  "user_id": 1,
  "task_id": "task456",
  "message": "analysis_started"
}
```

每个 HTTP 请求和 Celery 任务都应带 `request_id` 或 `task_id`，便于全链路追踪。

### 健康检查

```text
/health/live：服务进程是否活着
/health/ready：数据库、Redis、对象存储是否可用
```

### 验收标准

- 可以看到某个任务的完整生命周期。
- Worker 失败时能收到告警。
- 可以定位慢 API、慢 SQL 和积压队列。
- 用户报告问题时可以按 `task_id` 追踪。
